4.1 Project Methodology & Algorithms

4.1.1 Project Methodology (Step-by-Step Approach)

The implementation of Deep Truth followed the steps below.

1. Data Collection

  • What: Labelled real and fake media in three forms: face-swap and generated videos, AI-generated and real images, and genuine and spoofed speech recordings.
  • How: Public research datasets were downloaded and used for training, listed in Table 4.2. Video clips were taken in capped, balanced subsets so that training stayed within our compute budget.
  • Why: A detector can only recognise the kinds of fakes it has seen, so we combined datasets that cover different generation methods: classic face swaps, newer diffusion images, and speech synthesis.

2. Data Preprocessing

  • Missing Values: A submitted file is rejected if it is empty, too small to be real media, over the size limit, or if its first bytes do not match a supported media format. Audio with no usable soundtrack is reported as “no signal” instead of being guessed.
  • Duplicates: Training splits are made by identity: all clips derived from the same source person or video go into the same split, so a model is never tested on a face it has already seen. At run time, a SHA-256 hash of the uploaded bytes identifies duplicates, and a repeat upload is answered from the cache.
  • Normalization: Video frames are sampled (16 per clip), resized to 224 × 224 and normalised with the pre-trained model's mean and standard deviation. Images are resized to 224 × 224 with bicubic interpolation. Audio is converted by FFmpeg to 16 kHz mono and trimmed to its first 4 seconds. During training, videos were randomly flipped, brightened or darkened by up to 15%, and given light Gaussian noise so the models cope better with compression.
  • Class imbalance: Audio training data has nine spoofed clips for every genuine one, so the audio model was trained with a class-weighted loss.

3. Feature Extraction & Selection

  • What: The key inputs the models use are 16 frames per video, the cropped face region, 224 × 224 image patches, the speech waveform at 16 kHz, and 45 noise statistics per image (SRM).
  • How (frames and faces): The video preprocessor selects 16 frames spread across the clip, using fast seeking so cost does not grow with clip length. For face-based checkpoints, MTCNN finds faces in each frame and crops them with a 30% margin (for images, the largest face is used). The whole-frame model (genvideo) uses the centre-cropped full frame.
  • How (learned features): The transformers split each input into patches (ViT and ViViT) or process the waveform with convolution and attention layers (WavLM), and learn their own features. Only small LoRA adapters and a classification head are trained; the large pre-trained backbones stay mostly frozen.
  • How (noise statistics): A bank of five high-pass filters is applied to the image and 45 statistics of the filtered residual are computed. These form the input of a small neural network (45 → 32 → 16 → 2). Feature selection was not needed, because the transformers learn their own features and the 45 noise statistics are all used.

4. Model Training

  • Algorithm(s): ViT-B/16 with LoRA for images, ViViT-B/16×2 with LoRA for video, WavLM-Large with a 1024 → 256 → 64 → 2 head for audio, and an MLP for SRM features.
  • Training: Video data used an identity-aware 70% / 15% / 15% train / validation / test split. Models were checked after every epoch using validation AUC, and the best checkpoint was kept. Training stopped early after two epochs without improvement, or when AUC reached 0.97.
  • Why: Pre-trained transformers already understand images, video and speech well. LoRA lets us adapt each one to a new dataset while training only a few million parameters, which is what made it possible to train 14 specialised checkpoints on a single 24 GB GPU. Having one checkpoint per dataset also gives the system several independent opinions to combine.

5. Advanced Techniques

  • NLP: Not used. Deep Truth analyses images, video and audio, not text.
  • Blockchain: Not used. Tamper evidence for each case comes from storing the SHA-256 hash of the evidence and recording it in the PDF report.
  • Computer Vision: Face detection with MTCNN, patch-based transformers for images and video, and Grad-CAM heat maps. Grad-CAM is hooked on the layer-norm in front of the last attention block, because at the output of the last block the patch tokens no longer influence the classification and the map would be empty.
  • Speech processing: WavLM extracts speech representations, and the model's raw score is calibrated so that its own decision threshold maps to 0.5 (see Section 4.2).
  • Ensembling: Each modality combines its checkpoints with its own policy, and video cases combine frames and soundtrack in an audio-visual fusion step (Algorithm 2).
  • Asynchronous processing: Analysis does not run in the web server. A Redis-backed Celery queue hands each job to a worker, retries temporary failures, and caches finished verdicts.

6. Deployment

  • What: A FastAPI backend, a Next.js web console and a Chrome extension (see Sections 4.5 and 4.6).
  • How: Locally, as four cooperating processes: Redis, the API, an analysis worker and the web console. They are started from VS Code or from the command line.
  • Why: A user can check media from the page they are viewing, and an analyst can review cases and download a PDF report.

4.1.2 Algorithm

We document the three algorithms that carry the core logic of the system: the image ensemble that turns eight model scores into one verdict, the audio-visual fusion that decides a video's verdict, and the submission procedure that enforces the system's business rules before any model is run.

Table 4.3: Core algorithms

Algorithm NameDetails
ImageEnsembleDecision
(AI / classification)		Input: Scores: probability of fake from each image checkpoint; FaceDetected: whether MTCNN found a face
Output: Fake probability, policy used, confidence
Pseudocode:
1:  procedure ImageEnsembleDecision(Scores, FaceDetected)
2:    Gen  <- AUC-weighted mean of Scores from the generalist checkpoints
3:    Face <- AUC-weighted mean of Scores from the face checkpoints
4:    FaceTrusted <- FaceDetected and at least 2 face scores exist
5:    if Gen and Face are both missing then
6:      return NaN, "n/a", 0
7:    else if FaceTrusted and Gen exists then
8:      P <- max(Gen, Face); Policy <- "max_alarm"
9:    else if FaceDetected and Face exists and Gen exists then
10:     P <- 0.5 * Gen + 0.5 * Face; Policy <- "blend_50_50"
11:   else if Gen and Face both exist then
12:     P <- 0.8 * Gen + 0.2 * Face; Policy <- "weighted_80_20"
13:   else P <- Gen if it exists, otherwise Face
14:   end if
15:   Sigma <- standard deviation of all Scores
16:   Confidence <- clamp(1 - 2 * Sigma, 0, 1)   (0.5 for one score, 0 for none)
17:   return P, Policy, Confidence
18: end procedure
AudioVisualFusion
(Business rule / AI)		Input: Visual: fake probability and confidence from the frames; Audio: the same from the soundtrack, plus whether the audio model is validated
Output: Fused fake probability, manipulation type, deciding stream
Pseudocode:
1:  procedure AudioVisualFusion(Visual, Audio)
2:    for each stream S in {Visual, Audio} do
3:      if S.confidence > 0 then
4:        S.evidence <- 0.5 + S.reliability * (S.fakeProb - 0.5)
5:      end if
6:    end for
7:    Usable <- streams with confidence > 0
8:    if Usable is empty then return 0.5, "unknown"
9:    Deciding <- the usable stream with the highest evidence
10:   Fused <- Deciding.evidence
11:   if only one stream is usable then
12:     return Fused, "<stream>_only" or "none", Deciding
13:   end if
14:   VBand, ABand <- band(Visual.fakeProb), band(Audio.fakeProb)  // fake >= 0.65, real <= 0.35
15:   Type <- audio_and_visual if both fake; visual_only if only frames fake;
16:           audio_only if only audio fake; none if both real; else uncertain
17:   return Fused, Type, Deciding
18: end procedure
Note: reliability is 1.0 for a validated model and 0.25 for the current
experimental audio model, so it can raise doubt but not convict alone.
MediaSubmission
(Business rule)		Input: Request: media type, an uploaded file or a media URL, title
Output: A case that is queued or already finished, or a rejection with a reason
Pseudocode:
1:  procedure MediaSubmission(Request)
2:    if MediaType not in {image, video, audio} then reject 400
3:    if not exactly one of File, MediaUrl then reject 400
4:    if the queue broker is unreachable then reject 503
5:    if File is given then
6:      if content type not allowed or size > 500 MB then reject 422
7:      if the first bytes do not match MediaType then reject 422
8:      Hash <- SHA-256(File); Cached <- Cache.lookup(MediaType, Hash)
9:    else
10:     if scheme not in {http, https} or any resolved address is not public then reject 400
11:     Hash, Cached <- Cache.lookup via normalised URL
12:   end if
13:   Case <- create case with status "processing"
14:   if Cached then
15:     copy the stored verdict rows into Case; mark job "cached"; return Case
16:   else
17:     publish an analysis job to the queue; mark job "queued"; return Case
18:   end if
19: end procedure
Worker: on a temporary failure retry up to 3 times with exponential back-off
and jitter; on a permanent failure (missing file, unknown type) fail at once.

The audio model's decision threshold is very small (0.00028). That happens because the training data contains nine spoofed clips for every genuine one, which pushes the model's raw scores towards zero. At threshold 0.5 the model would miss many fake clips, so the system calibrates the raw score s against the threshold t with a two-part linear map: score 0.5 × s / t below the threshold, and 0.5 + 0.5 × (s − t) / (1 − t) above it. A score exactly at the threshold therefore becomes 0.5, which lines the audio output up with the 0.35 and 0.65 verdict bands used for images and video.

F1 is calculated from the recorded precision and recall as 2 × P × R / (P + R).

Confusion matrices and ROC curves. These were not saved during training for any model, so we can't reproduce them from stored results. We plan to compute them on a held-out labelled test set (see Chapter 6).

How the results relate to the objectives. The image models learned their own datasets well (AUC 0.95–0.996), which supports BO-2. The audio and SRM models are weaker, and the video models have no recorded metrics. Chapter 5 shows that on media outside the training data, detection accuracy is currently the weakest part of the system, and that is the main focus for the remaining development time.

4.3 Security Techniques

Deep Truth accepts files and links from strangers and runs expensive jobs for them, so most of its security work is at the gateway. The measures below are implemented; the weaknesses that remain are listed at the end.

Table 4.7: Security techniques

AreaTechniqueHow it is applied
Input validationFile-signature checkingThe first bytes of every upload and download are compared with the known signatures of JPEG, PNG, WebP, BMP, TIFF, MP4, MOV, AVI, WebM, MKV, MP3, WAV, FLAC, OGG and M4A. A ZIP file renamed .jpg is refused. The declared content type, size limit (500 MB) and minimum size are also checked.
Attack prevention (SSRF)Safe server-side downloadOnly http and https are allowed. Every address the host name resolves to must be public, so localhost, private networks and the cloud metadata address are refused. Redirects are followed manually and re-checked at each step. Downloads have a size cap, a timeout, and an optional host allowlist.
Attack prevention (abuse)Rate limitingA sliding-window limiter in Redis, run as one atomic script, allows 10 uploads, 60 changes and 300 reads per minute per client, and 5 open event streams. A rejected client receives HTTP 429 with a Retry-After header.
Attack prevention (XSS and injection)Escaping and parameterised queriesAll database access uses parameterised SQL. User text placed in the PDF report is escaped before layout. The web console renders text through React, which escapes by default.
Safe deserialisationJSON-only task messagesCelery accepts JSON only, so a message cannot make a worker run pickled code.
Cross-origin accessCORS policyAllowed origins are configurable, and browser-extension origins are matched by pattern.
Data integritySHA-256 content hashing and chain of custodyEach case records the SHA-256 of the evidence, the worker that analysed it, and the model versions and thresholds, and these appear in the PDF report while the job record is still available (the queue keeps it for 24 hours).
EncryptionNot implemented in this versionNo data is encrypted by the application itself (no AES or RSA). Integrity is protected with SHA-256 hashes. Encrypted transport (HTTPS/TLS) is required by SEC-2 and is planned for deployment behind a reverse proxy.
AuthenticationOperator profile (JWT planned)The console stores an operator name and email locally so that cases can be attributed. There is not yet a server-side login.

Known limitations. The API has no authentication, so any client that can reach it can read, edit or delete any case, and uploaded evidence is served from a public folder. The verdict of a case can also be edited through the API. Uploaded files are stored on disk instead of being kept only in memory, which does not satisfy requirement SEC-1. These are the first items in the future-work plan (Chapter 6): JWT-based login with per-case ownership, a read-only verdict with an audit log, and authorised access to evidence files.

Behaviour on this configuration. Because the machine has no GPU, an image takes about two to three minutes to analyse and a video about eight minutes, which is slower than the 5–15 seconds targeted in requirement PER-1. Repeated submissions are answered immediately from the cache. Only one worker should run per machine, as each one loads its own copy of the models.

Differences from the original design. The architecture chapter specifies PostgreSQL, production-grade Redis and HTTPS hosting. In this version, SQLite and a development Redis are used, which keeps the system easy to run for evaluation. Moving to PostgreSQL, a managed Redis, GPU workers and HTTPS is part of the future work in Chapter 6.
