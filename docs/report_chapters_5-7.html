Chapter 5: Testing and Evaluation

Once Deep Truth was running end to end, we spent time trying to break it. This chapter records what we tested, how we tested it, and what happened, including the cases where the system did not behave the way we hoped. We followed the four levels asked for in the template: unit testing of individual functions, functional testing of what a user or the browser extension can reach through the API, business rules testing with decision tables, and integration testing of the modules working together. Because Deep Truth is also a machine learning system, we added a section that evaluates the detection models themselves.

All tests were run on a development laptop with no GPU (Windows 10, Python 3.10, PyTorch CPU build) against the real code of the project. The backend tests used a temporary database and a temporary upload folder so that no real case data was touched. In total, 53 automated checks were run (33 unit, 16 functional and 4 integration), and all of them passed. Nine further PyTest tests for the audio-visual fusion layer also passed. The seven existing tests for the SRM noise filters (test_srm_filters.py, run with PyTest) also passed. The model evaluation in Section 5.5 is reported separately because, there, a failing result tells us about model quality rather than a software defect.

What we learned from these results.

  • The face-swap video models respond to faces, not to fakery. Five of the six video checkpoints rated the genuine phone video as fake, and the ensemble scored it higher than the AI-generated video. The only model meant to catch fully generated video (genvideo) gave the AI video just 3.7%.
  • The models are sensitive to the kind of media they were trained on. They were trained on research datasets such as FaceForensics++, Celeb-DF and DFDC. A portrait-orientation clip that WhatsApp has recompressed is very different from that material, and the project report itself lists heavy compression as a known limitation.
  • The audio model labels almost everything as fake. It was trained for one epoch on studio-quality speech from 2019, so ordinary phone microphone audio looks suspicious to it. It scored the genuine recording at 100% fake, so a high score from this engine is currently not strong evidence.
  • The image ensemble is diluted by weaker checkpoints. One model (ntire) was nearly certain, but averaging it with weaker ones pulled the result into the inconclusive band.
  • The SRM stream is too weak to rely on. Its 34% validation error rate agrees with what we saw, and that is why the system treats it as supporting information that never overrides the main verdict.

Chapter 6: Conclusion and Future Work

6.1 Conclusion

Deep Truth set out to give ordinary people a way to check whether a picture, clip or voice recording is real without leaving the page they are on. Chapter 1 described the problem: manipulated media spreads in seconds, but the tools that can expose it are slow, technical, and not part of how people actually browse. We answered with a complete system. A Chrome extension finds media on a page and sends it for analysis. A FastAPI gateway checks the file, a Redis-backed queue hands the work to Celery workers, and a set of trained models examines the content. The result comes back as a colour-coded verdict, and a web console keeps the case history and produces a PDF report.

Looking back at the objectives, most of the engineering goals were reached. One-click verification from the browser (BO-1) works end to end. The gateway validates files by their real content, limits abusive clients, and answers repeat submissions from a cache without running any model again (BO-3 and BO-6, in part). Analysis runs in the background through a queue with parallel workers and automatic retries, so the interface never freezes while a video is processed (BO-6). The detection side combines eight image checkpoints, six video checkpoints, a WavLM-based audio model and an SRM noise stream, each with its own fusion policy. Video cases now fuse the frame and soundtrack streams and name the type of manipulation found (BO-7). Image cases also return an artifact map showing which regions drove the verdict (BO-5), and the dashboard turns the evidence into a downloadable forensic report (BO-5 and BO-9). Automated testing, described in Chapter 5, passed in every area that depends only on software logic.

We also want to be honest about where the project falls short, because a forensic tool that overstates its certainty does more harm than good.

  • Detection accuracy on real-world media is not yet good enough. On our test files, only two of eight engine verdicts were correct. A genuine phone video was flagged as manipulated, the audio model flagged a real recording as fake, and the image ensemble could not decide on an AI-generated picture. The models were trained on research datasets and do not generalise well to compressed, phone-recorded media.
  • Fusion is implemented but cannot fix weak inputs. Video cases now combine the frames and the soundtrack and report the type of manipulation (BO-7). On our genuine phone video, however, both streams were wrong, so the fused verdict was wrong too. Fusion also has not yet been shown to improve accuracy over the best single model (FR9.1).
  • The response time target was not met. The report targets 5–15 seconds. On a CPU-only machine an image took about two to three minutes and a video about eight. A GPU would help, but this was not measured.
  • Privacy goal BO-8 is only partly achieved. Uploaded media is saved on the server rather than kept only in memory.
  • Access control is basic. The login screen only records who is operating the console; the API has no real authentication, and verdicts can be edited through the API.

Even with these limits, the project delivers something concrete. The infrastructure for collecting, queueing, analysing and reporting on media is complete, tested, and ready to take better models. When a stronger detector is trained, it can be plugged into the same pipeline without redesigning the system.

6.2 Future Work

The work we would do next falls into the following groups, roughly in order of importance.

Improving detection quality

  • Build a labelled test set of at least a hundred real and a hundred fake items per modality, including phone-recorded and WhatsApp- or Instagram-compressed media, and report accuracy, AUC, precision and recall for every model and for the full ensemble.
  • Retrain or fine-tune the whole-frame video model on current generators such as Sora, Veo, Kling and Runway, since fully generated video is the threat our report is built around, and add compression and re-encoding augmentation during training.
  • Retrain the audio model on more varied data (for example In-the-Wild, ASVspoof 5 and WaveFake) for more than one epoch, balance real and fake clips, and score long recordings in windows instead of only the first four seconds.
  • Replace the “highest score wins” rule for faces with a calibrated weighted combination, and recalibrate the checkpoint weights from measured validation results.
  • Replace or retrain the SRM stream so that it targets AI-generated images and not only splicing, or leave it as supporting information only.

Completing the fusion layer

  • Measure whether audio–visual fusion improves accuracy over the best single stream on a labelled test set, and tune the stream weights from those measurements. Add a lip-sync check between speech and mouth movement, which a score-level fusion cannot provide.
  • Sample video at one to two frames per second, as the report describes, with extra attention to the segments where faces and speech appear, instead of a fixed 16 frames.

Security, privacy and trust

  • Add real authentication (for example JWT-based login), check that a user can only open their own cases, and serve evidence files through an endpoint that checks permission.
  • Make the model verdict read-only, keep a separate analyst override field, and record every change in an append-only audit log, so that a report can be defended as evidence.
  • Link a page URL to a result only when the server itself downloaded the media from it, and expire these links, to prevent cache poisoning.
  • Process media in memory and delete it after analysis, as BO-8 requires, with an option for the user to keep a case.

Performance and scale

  • Run the workers on GPU hardware and measure latency against the 5–15 second target; consider smaller distilled models for the first quick verdict, followed by a deeper analysis in the background.
  • Move from SQLite to PostgreSQL, run Redis as a managed service, and load-test with 50 concurrent users to check PER-2.
  • Deploy behind HTTPS with several API instances and containerise the services for easy deployment.

User experience and reach

  • Run a usability study with students and journalists, and adjust the badge wording and colours according to their feedback.
  • Add Firefox and Edge support, a mobile companion app, and platform-specific handling for Instagram, YouTube and X.
  • Show explanations that ordinary users understand, such as which part of the picture looks synthetic and how sure the system is, so that “inconclusive” results are clearly presented.

Longer-term research directions

  • Add provenance signals such as C2PA content credentials and watermark detection as an additional evidence stream.
  • Use continual learning, so that new generators can be added without retraining everything from scratch, and report confidence intervals along with each verdict.
  • Explore explainable detection with large multimodal models that localise and describe the manipulation in words.
